## Goal
"Edit Details" on Account Details (106) becomes a real button: it turns Bank Name, Branch Name and Account Type into fields on the same page, with Save and Cancel (US-12 criteria 4 to 9, #26). Save stores them through the app's first account write, `PATCH /api/accounts/:accountId`: the user from the session, the account from the URL, one `UPDATE` with both in its `WHERE`, the names trimmed and checked by one shared rule that the form and the API both use. Every write behind the session guard, the goal `PUT` included, carries the user the tab shows and is refused with 409 when the session is someone else's (#119), which closes #110's stale-tab case.

- How these notes are met, and where this file chooses (each in the Human checkpoint):
  - **The write guard: #119, answered as proposed with one condition.** Every write behind the session guard carries `X-Expected-User` with the email of the user the tab shows; the session guard answers 400 without it and 409 ("Another user is signed in. Nothing was saved.") when it is not the session user's, before anything is read or written; public writes and reads are not guarded; on that 409 the tab shows the message and asks for the session again, which switches it to the signed-in user (task 014). The condition: the header is compared with the session user's email in the normalized form the database stores (#15: parsed with the shared `emailSchema`, trimmed and lowercased as sign up and login store it), never the raw header, so a header that differs from the stored email only in case is the same user and the write succeeds (T6, T7). Why the goal PUT needs it and the account PATCH less so: the PATCH names the account in its path, so a stale tab's PATCH with another user's session already gets the account's 404; the goal PUT names nothing, so without the guard it writes into the other user's goal (#110). Both get it, from one check, and so does every later write (tasks 025 to 030), with nothing to add per route.
  - **The card network: #120 a, answered: no rule.** The network stays as stored and its logo shows with any type, as #24 reads. Nothing in this task's Scope changes the logo.
  - **The name rules: #120 b, answered as proposed: the character count in code points**, because (1) the form and the API count the same in every runtime (graphemes follow each runtime's Unicode data, so Chrome and Node could disagree at the limit on a new emoji sequence: the form accepts and the API refuses, or the other way round); (2) the size is bounded (100 code points are at most 400 bytes of UTF-8, while one grapheme can carry any number of combining marks, so a grapheme limit would need a second one); (3) SQLite's `length()` counts code points, so a test can read the stored length in SQL. The cost: an emoji sequence counts as several characters (a family emoji 5, a flag 2), and an accent typed as two code points counts 2; letters of every script as keyboards type them count 1. No HTML `maxlength` on the fields (it counts UTF-16 units and would stop typing early): the rule runs on Save, as US-12 criterion 7 says. Answered in #120 b with it: the trim of JavaScript's `trim()` (Unicode White_Space and the BOM), a name with nothing visible left (only whitespace, control or format characters, such as a zero-width space) counted as empty, a control character inside a name (a tab) refused, and the texts after #95 a.

The answer is the account's details, the same five fields as `GET /api/accounts/:accountId` (the stored, trimmed names and the balance), so the page shows the stored values without asking again.
