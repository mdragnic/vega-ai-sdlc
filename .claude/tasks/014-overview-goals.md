## Goal
The Overview Goals card shows the signed-in user's savings goal for the current month in their time zone: the Target with the pencil button, the month, Target Achieved and This month Target, and the Target vs Achievement gauge at the progress the backend calculates. The pencil opens popup 104.1, which creates or updates that month's goal through the app's first write endpoint, with the amount rules in shared schemas and money in integer cents. When a session ends, or another tab switches the signed-in user, no earlier user's data or pending write stays in this tab's caches.

## Scope
Choices marked "(#108 x)" follow #108 (closed, Marko, 2026-10-26: all four as proposed).

- **Shared** (`@finebank/shared`), `shared/src/contract/savings-goal.ts` (new, one file per resource), exported through the contract index:
  - `goalMonthSchema`: `YYYY-MM`, month `01` to `12`.
  - The amount rules, once (#31, #74, #85): `goalTargetSchema`, a `moneySchema` whose cents are above 0 and at most 100,000,000,000 (`$1,000,000,000.00`, inclusive); `goalPresentSchema`, a `moneySchema` whose cents are 0 or more and at most the same maximum. `moneySchema` allows negatives, so the non-negative rule is added here; it already rejects cents that are not safe integers. Each rule reports on the field itself (`target`, `present`), not on `cents`, with the texts of #108 a; one message per field, its first failing rule (as #95).
  - `savingsGoalRequestSchema`: `{ month, target, present }` (#108 d); unknown keys are dropped, so a `userId` in a body has no effect.
  - `savingsGoalFormSchema`: the popup's two text fields `{ target, present }` to the amounts: each text read with `parseAmountInput` (#64, #84); an empty Target (or a lone `.`) fails with the "required" text, an empty Present gives 0 cents (#84 b); then the same `goalTargetSchema` and `goalPresentSchema` rules. The popup uses it through `zodResolver`, so the form and the API check one set of rules.
  - `savingsGoalSchema`: `{ target, present, progress }`, `progress` a number from 0 to 1. `savingsGoalResponseSchema`: `{ month, goal }`, `goal` a `savingsGoalSchema` or `null` (#58, #85).
  - `savingsGoalsContract.current`: `GET /savings-goals/current`, no body. `savingsGoalsContract.save`: `PUT /savings-goals`, body `savingsGoalRequestSchema`, response `savingsGoalResponseSchema`. Tasks 025 to 027 extend this file for the Goals page.
- **Backend** (`backend/src/goals/`, a `GoalsModule` registered in `AppModule`, with `TypeOrmModule.forFeature([SavingsGoal])`; the table exists, no migration):
  - `current-month.ts`: `currentMonthIn(now, timeZone)`, the `YYYY-MM` of `todayIn(now, timeZone)` (#54, #80).
  - `savings-goals.service.ts`: `SavingsGoalsService`:
    - `current(userId, timeZone)`: the month from `Clock` and the zone; the user's row for that month, always selected by `user_id` and `month`; `{ month, goal: null }` when there is none (#58, #85); otherwise the Target, the Present and `progress = goalProgress(present, target)` (#18, #31), money as `{ cents, currency: 'USD' }` (#96).
    - `save(userId, timeZone, request)`: the request's month must be the current month in the zone; any other month is answered with 409 and the #108 d text, nothing stored (#108 d). Creates the month's row when there is none, otherwise updates its Target and Present, keyed on the user and the month (the table's unique constraint), in one transaction; never another user's row, never a second row for a month (#58). Returns what `current` returns.
    - The user ID comes only from the session; nothing in a request names a user or a goal ID.
  - `savings-goals.controller.ts`: `SavingsGoalsController`, both paths from `savingsGoalsContract`, the user from `@CurrentUser()` (#39, #75), the zone from `@TimeZone()` (400 when missing or not a zone). The `PUT` body is validated by `savingsGoalRequestSchema` through the global validation pipe: 400 in the shared shape with `fieldErrors` keyed `month`, `target` and `present`. Behind the global `SessionGuard` (401 signed out) and Nest's CSRF protection (403 for a cross-site write, before the route runs, task 007). Responds 200 with `savingsGoalResponseSchema`: no row ID or user ID.

Given a Present of $25,000.00 on a Target of $20,000.00, then the progress is 1, the whole arc is teal and the center reads `$25k`; given a Present of $0.00, then no arc shows and the center reads `$0` (US-06 criteria 3 and 4; #11, #18, #31).
3. Given the backend clock at 2026-10-31T23:30:00Z, then in Europe/Belgrade (1 Nov there) the card shows "Nov, 2026" with `$17,000.00` achieved, and in America/New_York (31 Oct there) "Oct, 2026" with `$16,250.00` (#54, #58, #80).
4. Given I click the pencil, then popup 104.1 opens over the content area with the X, "Target Amounts" showing `$20000`, "Present Amounts" showing `$16250` and "Save"; only the content area is dimmed, the sidebar and header are blocked, and focus is inside the popup, on the Target field. A goal of $1,250.50 shows `$1250.50` (US-06 criteria 5, 6 and 13; #31, #35, #64, #90).
5. Given the popup with edited values, when I click X, press Esc or click the dimmed area, then it closes, nothing is saved, focus returns to the pencil, and reopening shows the saved values (US-06 criterion 7; #35).
6. Given I enter Target `25000.5` and clear Present, when I click Save, then `PUT /api/savings-goals` sends `{ month: "2026-10", target: { cents: 2500050, currency: "USD" }, present: { cents: 0, currency: "USD" } }`, the popup closes, and the card shows `$25,000.50` and `$0.00` achieved; after a reload the same; reopening shows `$25000.50` and `$0` (US-06 criteria 8 and 13; #11, #31, #84).
7. 8. Given I type in either field, then digits and one decimal point with at most 2 decimals stand; a comma, a letter, `$`, `-`, a space and a third decimal are rejected, also when pasted (US-06 criterion 14; #64; task 005's control).
9. Given I click Save, while the request runs, then Save is disabled with its spinner and keeps keyboard focus, and another click or Enter sends no second request. Given the server answers 500 or the network fails, then "Something went wrong." shows above Save; given a 4xx in the shared shape, its message; given a 400 with field errors, they show under their fields. The popup stays open with the typed values (US-06 criterion 10; #6, #97 a).
10. Given the current month has no goal, then the card shows "No goal for this month" with the pencil (laid out per #108 c). Save with Target empty shows the required message; with Target `500` and Present empty it creates the month's goal ($500.00, $0.00) and the card shows it, with nothing taken from the previous month (US-06 criteria 11 and 12; #58, #69, #71, #84, #85, #90 b).
11. Given `GET /api/savings-goals/current` with a session and a valid `X-Time-Zone`, then it answers 200 with `savingsGoalResponseSchema`: `month` `2026-10` and the goal in integer cents with `USD` and `progress` 0.8125; for a month with no row, `goal: null`. 12. Given `PUT /api/savings-goals`, then a valid body creates the month's goal or updates it (still one row for the user and month) and answers 200 with the saved goal. 13. Given two users, when one saves a goal, then only their row changes; the other's `GET` answers as before. A `userId` in the body or the query changes nothing, and no route takes a user or goal ID (#39, #46).
14. Given the goal, then `progress` is calculated in the backend with `goalProgress`; the frontend formats the cents and draws the progress it gets, with no arithmetic on amounts; the backend reads "now" only from `Clock` (#11, #18, #31, #54, #92).

16. Given a session ends (logout, or a 401 from any request, also from the save), then the mutation cache holds no mutation other than the session's own, and no goal amounts remain in the query or the mutation cache (#3, #39; task 009 review).
17. 20. Given Overview at 1440x1024, then the Goals card is at x 680–1032 and y 144–376, the top row 232 high, its content where 104 draws it.
