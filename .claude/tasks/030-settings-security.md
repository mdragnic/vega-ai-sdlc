Answered by Marko on 2026-11-07: (a), (b) and (c) as proposed (the References' decision list gives each answer).
  - **The endpoint:** `PUT /api/auth/password` (`authContract.changePassword`), JSON (#76's multipart is Update Profile's only), the body `{ currentPassword, newPassword }` (`passwordChangeRequestSchema`, unknown keys dropped), answering 204 with no body. `PUT`: it replaces the session user's one password. In `authContract`, beside sign up and login, whose password rules it reuses; behind the session guard (not `@Public()`), so the #119 guard covers it with nothing added.
  - **The rules, one shared module (#74):** `passwordChangeRequestSchema`: `currentPassword` by login's rule (required, at most 128 characters: it is hashed by the check, #95), `newPassword` by sign up's `newPasswordSchema` (#15, #95), then the new one different from the current one, compared exactly as typed (#34; passwords are never trimmed or changed, #95 c). The form's schema `passwordChangeFormSchema` is the request schema extended with `retypePassword` and its match with `newPassword`, so the form and the API share every rule but the retype, which only the form has (the backend never receives it: a server check of two copies typed in one form adds nothing). One message per field, its first failing rule (#95 a); the "different" check runs only when New Password passed its own rules. The texts (#34, #95, #129 b): Old Password login's, "Password is required" and "Password must be at most 128 characters"; New Password sign up's, then "New password must be different from the old password"; Retype Password "Passwords do not match", also when it is empty and New Password is not, and nothing when both are empty (New Password shows "Password is required").
  - **The current password checked with scrypt, both hashes outside any transaction:** after the guards and the schema, the service reads the session user's `password_hash` by ID, runs `PasswordHasher.verify` (outside any transaction, as login), and only when it matches computes the new hash with `PasswordHasher.hash` (outside any transaction, as sign up), so a wrong password costs one scrypt run, not two. Then one transaction: `UPDATE users SET password_hash = <new> WHERE id = <session user> AND password_hash = <the hash just verified>` and `DELETE FROM sessions WHERE user_id = <session user> AND token_hash <> <the presented session's hash>` (#129 a). If the `UPDATE` changes no row (the hash changed after the check: a change in another browser, a Google takeover #104), nothing is written and the answer is the wrong-password 400: what was typed is no longer the current password. This is login's re-read of the hash (#104) as a compare and set in the `UPDATE`'s own `WHERE`.
  - **The session:** the current session stays (#34, #75): its row and token are untouched and the response sets no cookie, so a "Keep me signed in" choice and its expiry stay as they were. Tabs of the same browser share that session (one cookie) and stay signed in. Every other session of the user is deleted in the same transaction (#129 a); another browser of the user is then signed out at its next request (401, Login with its return target, #3), with no message (not designed). `docs/architecture.md` records it in the same commit.
  - **A Google-only user (#2, #104): settled, no question.** #2 ("Google-only users have no password: the password section in Settings, Security is hidden for them"), #34 (the same) and US-19 criterion 3 ("the three password fields and 'Update Password' ... hidden") settle the tab: it shows the Phone Number alone, read-only, in the first field's place (no gap where the section would be), no button, nothing else; the user cannot set a password there (#2: they have none). The frontend knows from `profileSchema`'s new `hasPassword` (true when `password_hash` is not NULL), read with the profile the panel already needs for the phone. A direct `PUT /api/auth/password` from a Google-only user runs `verify` against the dummy hash, as login does for them, and gets the wrong-password 400 with nothing stored: no special path. If a Google takeover in another tab of the same browser makes the user Google-only (#104 replaces the session, so this tab stays signed in), the panel follows the profile's next read (window focus) and hides the section.
  - **A wrong current password:** 400 `{"message":"Current password is incorrect","fieldErrors":{"currentPassword":"Current password is incorrect"}}` (#34's text; the shape of the username-taken 409, #74); nothing stored, no session changed. The form shows it under Old Password with focus there; the typed values stay (#6).
  - **Repeated wrong attempts: not limited, because #14 puts brute-force protection out of scope for now.** The login form, which needs no session at all, takes any number of attempts by #14, so a limit on this endpoint alone would not protect the password. Each attempt here also needs a valid session cookie, a same-site request (CSRF) and the user's email in `X-Expected-User`, and costs one scrypt verification (N = 2^17, about 128 MB and a few hundred milliseconds), the same cost as a login. Recorded in `docs/architecture.md`'s accepted constraints with login's, so a later brute-force protection covers both.
  - **The write per #119 and the password's privacy:** the user only from the session (`@CurrentUser()`; a `userId`, `email` or `passwordHash` key in the body is dropped by the schema and names nobody); the #119 guard (400 without `X-Expected-User`, 409 for another user's email, before the body is read); CSRF (403) first.
